FILE: src/app.ts
CATEGORY: Bug
SEVERITY: High
ISSUE: CORS for the public /api/chat widget endpoint is silently overwritten by
the global dashboard CORS, breaking cross-origin widget embedding.
EVIDENCE: Line 22 mounts `cors({ origin: "*", ... })` ONLY for "/api/chat", but
line 38 then mounts `dashboardCors` (cors with a fixed FRONTEND_URL +
credentials:true) globally with no path restriction. For any /api/chat request
BOTH middlewares run (mount order: chat-cors first, then dashboardCors second),
so dashboardCors overwrites the `Access-Control-Allow-Origin` header with the
specific frontend origin. The comment at lines 18-21 explicitly states CORS must
be open because the widget is embedded from ANY website — the actual behavior is
the opposite, so third-party sites get blocked by the browser.
SUGGESTED FIX: Apply dashboardCors only to non-chat routes (e.g. mount it with a
path whitelist or exclude /api/chat), or register the open /api/chat CORS AFTER
the global one. Verify with an actual cross-origin preflight test.

FILE: src/app.ts
CATEGORY: Optimization / Security
SEVERITY: Medium
ISSUE: No request body size limit and no rate limiting; rate-limit dependencies
are present but never wired up.
EVIDENCE: Line 40 `app.use(express.json())` has no `limit` option (DoS via large
payloads). `express-rate-limit` and `redis-rate-limiter` are in package.json but
`grep` shows zero usage anywhere in src. Auth (signup/login) and the public
/api/chat endpoint are therefore unthrottled → credential brute-force and chatbot
API abuse are possible.
SUGGESTED FIX: Add `express.json({ limit: "1mb" })` and apply rate limiting to
/auth/* (especially login/signup) and /api/chat (per apiKey). Remove unused
rate-limit deps if not adopted.

FILE: src/middleware/auth.middleware.ts (and src/controllers/auth.controller.ts)
CATEGORY: Bug (Security)
SEVERITY: High
ISSUE: JWT secrets fall back to hard-coded weak defaults when env vars are unset.
EVIDENCE: auth.middleware.ts:8 `const JWT_SECRET = process.env.JWT_SECRET ||
"secret"`; auth.controller.ts:8-9 `JWT_SECRET = ... || "secret"` and
`REFRESH_SECRET = ... || "refresh_secret"`. If JWT_SECRET/JWT_REFRESH_SECRET are
not configured, attackers can forge valid tokens with the known word "secret".
The same default is duplicated in two files (drift risk).
SUGGESTED FIX: Fail fast at boot if JWT_SECRET/REFRESH_SECRET are missing in
production. Never ship a usable fallback. Centralize secret loading in one config
module.

FILE: src/controllers/auth.controller.ts
CATEGORY: Bug (Security)
SEVERITY: Medium
ISSUE: Refresh tokens are stored as plaintext, not hashed, and are never rotated
or invalidated on use.
EVIDENCE: login() stores `tokenHash: refreshToken` (the raw JWT) at lines 64-70.
The column is literally named `tokenHash` but holds the cleartext token. No
refresh-token rotation is implemented despite ErrorCode.AUTH_REFRESH_TOKEN_REUSED
existing in utils/error.ts. A DB leak yields directly usable sessions.
SUGGESTED FIX: Store a hash (e.g. sha-256) of the refresh token; implement
rotation (issue new token + invalidate old on refresh). Verify on refresh by
hashing the incoming token.

FILE: src/controllers/chat.controller.ts
CATEGORY: Bug
SEVERITY: Medium
ISSUE: When `sessionId` is omitted, Prisma ignores the `undefined` value in
`where`, collapsing all session-less conversations for a chatbot into one.
EVIDENCE: Lines 165-172 and 199-206:
`prisma.conversation.findFirst({ where: { chatbotId, sessionId } })`. Prisma
treats `sessionId: undefined` as "do not filter", so it returns the first
conversation for that chatbot regardless of session. The subsequent
`create({ sessionId: sessionId ?? "" })` stores "" while the lookup ignores
sessionId — inconsistent and merges unrelated user threads.
SUGGESTED FIX: Normalize missing sessionId explicitly (e.g. generate a uuid when
absent) and always pass a concrete string, or filter with a defined fallback.

SEVERITY: Medium

EVIDENCE: queue/crawl.worker.ts processes pages sequentially and inserts

FILE: src/services/indexing.service.ts
CATEGORY: Optimization
SEVERITY: Medium
ISSUE: Chunks are inserted one-by-one with a separate DB round-trip per chunk.
EVIDENCE: Lines 58-95 loop over docs and call `prisma.$executeRawUnsafe(INSERT...)`

FILE: src/prisma/schema.prisma
CATEGORY: Optimization
SEVERITY: High
ISSUE: No database index on the frequently-filtered `chatbotId` scalar columns.
EVIDENCE: Chunk.chatbotId, Conversation.chatbotId, CrawlPage.chatbotId, and
MissedQuery.chatbotId are all queried constantly (every chat request, every
dashboard stat, sparse/dense retrieval WHERE clauses) but none have an explicit
`@@index([chatbotId])`. Prisma does not auto-index relation scalar fields. As data
grows, these become sequential scans. (Chunk also JOINs CrawlPage on pageId — that
is covered by the PK.)
SUGGESTED FIX: Add `@@index([chatbotId])` to Chunk, Conversation, CrawlPage, and
MissedQuery (and consider a composite index on Chunk(chatbotId, embedding) usage
patterns). Also add an index on Conversation(sessionId) and
MissedQuery(chatbotId, askedAt).

SUMMARY
================================================================================
Total issues by category:
  Bugs (incl. security):           12
  Simplification / Dead code:       7
  Optimization:                     5
  (Some items span categories; counted once under primary category.)

Top 3 most critical issues:
  1. [High] CORS override in app.ts breaks the public /api/chat widget
     (cross-origin embedding silently blocked) — src/app.ts:22 vs :38.
  2. [High] Hard-coded fallback JWT secrets ("secret"/"refresh_secret") in
     auth.middleware.ts:8 and auth.controller.ts:8-9 — token forgery risk if
     env not set.
  3. [High] Missing DB indexes on chatbotId (Chunk/Conversation/CrawlPage/
     MissedQuery) in prisma/schema.prisma — sequential scans as data grows, and
     missing rate limiting on auth/chat (deps present but unused).

General architectural observations:
  - Error handling is inconsistent: two competing AppError implementations
    (utils/errors.ts vs utils/error.ts) and controllers mostly use manual
    res.status().json() instead of a typed error system; the elaborate
    utils/error.ts hierarchy is entirely unused.
  - No rate limiting is wired despite express-rate-limit & redis-rate-limiter
    being dependencies.
  - Several "dead" utilities exist (zodMiddleware, getRedis, chatRequestSchema,
    utils/error.ts) indicating partially-refactored code.
  - Retrieval pipeline is well-structured with timeouts per external call, but
    timeout coverage is incomplete (LLM generation + Anthropic path unbounded),
    and Promise.race leaves dangling promises.
  - Cascade deletes are correctly configured (Chunk.pageId, Chatbot.* onDelete:
    Cascade), so deletePage/deleteChatbot do NOT orphan rows — good. The real
    risk there is crawl-worker retry duplication, not missing cascades.
  - The codebase is TypeScript but ships no input validation on the most
    exposed endpoint (/api/chat); rely on zod schemas uniformly.
