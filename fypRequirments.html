ChatEmbed — FYP Blueprint

A SaaS platform that lets anyone embed a RAG-powered AI chatbot on their website by simply entering a URL. No coding required for the end user. This document is the single source of truth for architecture, schema, flow, and feature decisions.

Next.js 14 Express + TypeScript FastAPI + Crawl4AI Supabase + pgvector BullMQ + Redis Gemini Flash + Embeddings

What it does in one sentence

User pastes a URL → app crawls the site → chunks + embeds content → user gets a deployable chatbot widget that answers questions using their website's content.

Core Value Props

⚡ Zero-config for end user
Paste URL, name your bot, get a script tag. Done.
🎯 Accurate RAG answers
Hybrid semantic + keyword search, not just cosine similarity.
📊 Missed queries tracking
See what your bot couldn't answer so you can fix content gaps.
🧪 Playground mode
Test your bot before deploying it publicly.

Why not separate vector DB (Pinecone, Weaviate)? For a FYP, a separate vector DB adds ops complexity with zero benefit. pgvector on Supabase lets you do SELECT with metadata filters + vector search in one query. Pinecone free tier also has index limits. Stay with Supabase.
Embedding dims: Use output_dimensionality=768 for Gemini text-embedding-004. You already fixed the 1536 cap issue — 768 is actually the native dim for this model, lighter on storage, faster on HNSW index.

Service-to-Service Auth

Express → Python uses a shared X-Internal-Key header (env var on both). Python service is not exposed publicly — only Express can call it. If deploying on same VPS, Python runs on localhost:8000 and is firewalled from outside.

-- HNSW index for fast cosine similarity search
CREATE INDEX chunks_embedding_idx ON chunks
  USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);

-- GIN index for full-text search
CREATE INDEX chunks_fts_idx ON chunks USING gin(fts);

-- Auto-populate fts column on insert/update
CREATE TRIGGER chunks_fts_trigger
  BEFORE INSERT OR UPDATE ON chunks
  FOR EACH ROW EXECUTE FUNCTION
  tsvector_update_trigger(fts, 'pg_catalog.english', content);

RAG Pipeline — The Right Way

Strategy: Hybrid RAG = Semantic search + Full-text search, fused with RRF. Pure cosine similarity misses exact keyword matches (product names, error codes). Pure BM25 misses paraphrased questions. Combining both gives the best results for markdown content.

Step 1 — Chunking Strategy (Critical)

Since your content is markdown, section-aware chunking beats fixed-size chunking. Split at headings, not at character count.

# Python chunking logic (in your FastAPI service)
import re

def chunk_markdown(markdown: str, max_tokens: int = 400) -> list[dict]:
    """Split markdown by headings, then by token limit if section is too long."""
    chunks = []
    current_heading = ""
    current_text = []

    for line in markdown.splitlines():
        # Detect heading
        heading_match = re.match(r'^(#{1,3})\s+(.+)', line)
        if heading_match:
            # flush current chunk
            if current_text:
                chunks.append({
                    "heading": current_heading,
                    "content": "\n".join(current_text).strip()
                })
                current_text = []
            current_heading = heading_match.group(2)
        else:
            if line.strip():
                current_text.append(line)

    # flush last chunk
    if current_text:
        chunks.append({
            "heading": current_heading,
            "content": "\n".join(current_text).strip()
        })

    return [c for c in chunks if len(c["content"]) > 50]  # skip tiny chunks
Overlap: Add 1–2 sentences of overlap between chunks so context isn't lost at chunk boundaries. Simple trick: append the last sentence of chunk N to the start of chunk N+1.

Step 2 — Embedding (Node.js, Express worker)

// services/embedding.service.ts
import { GoogleGenerativeAI } from "@google/generative-ai";

const genai = new GoogleGenerativeAI(process.env.GEMINI_API_KEY!);
const model = genai.getGenerativeModel({ model: "text-embedding-004" });

export async function embedText(text: string): Promise<number[]> {
  const result = await model.embedContent({
    content: { parts: [{ text }], role: "user" },
    taskType: "RETRIEVAL_DOCUMENT",     // for indexing chunks
    outputDimensionality: 768,
  });
  return result.embedding.values;
}

export async function embedQuery(text: string): Promise<number[]> {
  const result = await model.embedContent({
    content: { parts: [{ text }], role: "user" },
    taskType: "RETRIEVAL_QUERY",          // different task type for queries!
    outputDimensionality: 768,
  });
  return result.embedding.values;
}

Step 3 — Hybrid Search with RRF (the secret sauce)

-- services/search.sql (run via pg query in Express)

WITH
-- 1. Semantic search: top 20 by cosine similarity
semantic AS (
  SELECT id, content, heading, url,
         1 - (embedding <=> $1::vector) AS score,
         ROW_NUMBER() OVER (ORDER BY embedding <=> $1::vector) AS rank
  FROM chunks
  JOIN crawl_pages ON chunks.page_id = crawl_pages.id
  WHERE chunks.chatbot_id = $2
  ORDER BY embedding <=> $1::vector
  LIMIT 20
),
-- 2. Full-text search: top 20 by BM25-like ranking
keyword AS (
  SELECT id, content, heading, url,
         ts_rank(fts, plainto_tsquery('english', $3)) AS score,
         ROW_NUMBER() OVER (
           ORDER BY ts_rank(fts, plainto_tsquery('english', $3)) DESC
         ) AS rank
  FROM chunks
  JOIN crawl_pages ON chunks.page_id = crawl_pages.id
  WHERE chunks.chatbot_id = $2
    AND fts @@ plainto_tsquery('english', $3)
  ORDER BY score DESC
  LIMIT 20
),
-- 3. RRF fusion: 1/(k + rank), k=60 is standard
fused AS (
  SELECT
    COALESCE(s.id, k.id) AS id,
    COALESCE(s.content, k.content) AS content,
    COALESCE(s.heading, k.heading) AS heading,
    COALESCE(s.url, k.url) AS url,
    COALESCE(1.0/(60 + s.rank), 0) + COALESCE(1.0/(60 + k.rank), 0) AS rrf_score,
    COALESCE(s.score, 0) AS semantic_score
  FROM semantic s
  FULL OUTER JOIN keyword k ON s.id = k.id
)
SELECT * FROM fused
ORDER BY rrf_score DESC
LIMIT 5;  -- top 5 chunks go into context

Step 4 — LLM Generation (Gemini Flash)

// services/chat.service.ts
export async function generateAnswer(
  query: string,
  chunks: { content: string; heading: string; url: string }[],
  chatbot: { name: string; system_prompt: string; welcome_message: string }
): Promise<{ answer: string; sources: string[] }> {

  const context = chunks
    .map((c, i) => `[Source ${i+1}] ${c.heading ? `(${c.heading})\n` : ""}${c.content}`)
    .join("\n\n---\n\n");

  const systemPrompt = chatbot.system_prompt || `You are ${chatbot.name}, 
a helpful assistant. Answer only using the provided context. 
If the answer isn't in the context, say: "I don't have information 
about that. Please contact support." Keep answers concise and helpful.`;

  const prompt = `${systemPrompt}

CONTEXT:
${context}

USER QUESTION: ${query}

Answer based only on the context above:`;

  const model = genai.getGenerativeModel({ model: "gemini-1.5-flash" });
  const result = await model.generateContent(prompt);

  return {
    answer: result.response.text(),
    sources: [...new Set(chunks.map(c => c.url))]
  };
}
Missed query threshold: If semantic_score < 0.72 (cosine similarity), the bot doesn't have good context. Still answer but log it to missed_queries. Tune this number after testing — 0.70–0.75 is a safe starting range.

Background Jobs (BullMQ)

Job: crawl-and-index

// workers/crawl.worker.ts
import { Worker } from "bullmq";

const crawlWorker = new Worker("crawl-queue", async (job) => {
  const { chatbotId, url } = job.data;

  // 1. Update status → crawling
  await db.query("UPDATE chatbots SET status='crawling' WHERE id=$1", [chatbotId]);

  // 2. Call Python service — get markdown pages
  const { data: pages } = await pythonClient.post("/crawl", { url, max_pages: 100 });
  // pages = [{ url, title, markdown }, ...]

  // 3. Update status → indexing
  await db.query("UPDATE chatbots SET status='indexing', pages_crawled=$1 WHERE id=$2",
    [pages.length, chatbotId]);

  // 4. Chunk + embed each page
  let chunkCount = 0;
  for (const page of pages) {
    const pageRow = await db.query(
      "INSERT INTO crawl_pages(chatbot_id, url, title) VALUES($1,$2,$3) RETURNING id",
      [chatbotId, page.url, page.title]
    );
    const chunks = chunkMarkdown(page.markdown);  // your chunking util

    for (const chunk of chunks) {
      const embedding = await embedText(chunk.content);
      await db.query(`
        INSERT INTO chunks(chatbot_id, page_id, content, heading, embedding)
        VALUES($1, $2, $3, $4, $5)
      `, [chatbotId, pageRow.rows[0].id, chunk.content, chunk.heading, JSON.stringify(embedding)]);
      chunkCount++;
    }

    // Update progress so status polling shows progress
    await job.updateProgress({ done: chunkCount, total: pages.length * 10 });
  }

  // 5. Done!
  await db.query("UPDATE chatbots SET status='ready' WHERE id=$1", [chatbotId]);

}, { connection: redisConnection, concurrency: 2 }); // max 2 crawls at once

crawlWorker.on("failed", async (job, err) => {
  await db.query("UPDATE chatbots SET status='failed' WHERE id=$1", [job?.data.chatbotId]);
});
Rate limit Gemini embeddings: text-embedding-004 free tier allows 1,500 requests/min. If you're embedding many chunks, add a small delay (await sleep(50)) between embed calls, or batch them 5 at a time.

Missed Queries System

This is a key differentiator for your FYP — it shows that the system is self-aware about its knowledge gaps.

Detection Logic

// In your /api/chat handler, after hybrid search:
const MISSED_THRESHOLD = 0.72;

const topChunk = searchResults[0];
const isMissed = !topChunk || topChunk.semantic_score < MISSED_THRESHOLD;

if (isMissed) {
  // Log it — don't block the response
  db.query(
    "INSERT INTO missed_queries(chatbot_id, query, top_score, session_id) VALUES($1,$2,$3,$4)",
    [chatbotId, query, topChunk?.semantic_score ?? 0, sessionId]
  ).catch(console.error);  // fire and forget — don't slow down response
}

// Always generate answer (Gemini may still give partial help)
const answer = await generateAnswer(query, searchResults.slice(0, 5), chatbot);

Build Phases (Realistic Timeline)

You start FYP in mid-July. If you give this ~12 weeks before thesis writing begins, here's a realistic split.
PhaseWhat to buildTime
Phase 1DB schema + Express auth (JWT + refresh) + Supabase setupWeek 1
Phase 2Crawler worker: Python → BullMQ → chunk → embed → pgvectorWeek 2–3
Phase 3RAG chat endpoint: hybrid search + Gemini FlashWeek 3–4
Phase 4Next.js dashboard: auth pages, chatbot creation wizard, crawl statusWeek 4–6
Phase 5Playground page + missed queries systemWeek 6–7
Phase 6Embed widget JS (Vite), deploy page, script tag generationWeek 7–8
Phase 7Polish: settings page, recrawl, conversations list, statsWeek 9–10
Phase 8Testing, FYP demo prep, thesis writing beginsWeek 11–12
Build order rule: Always build data → API → UI. Never start a UI page before its API works. The worst FYP mistake is building a pretty frontend that has no working backend behind it.
